# 決済ドメイン ユビキタス言語辞書

このドキュメントは、決済ドメインの業務知識(誰が・何を・どういうルールで行うか)を、Spring Boot・パッケージ構成・Outbox・ArchUnitといった技術的な実装方式から**独立して**記述したものです。ここで定義した用語・業務ルールが、[requirements.md](./requirements.md)の各要件の根拠となり、さらに[design.md](./design.md)における集約・値オブジェクト・不変条件の実装根拠になります。

用語や業務ルールを変更する必要が生じた場合は、まず本書を更新してからシステム設計書側を追随させる
---

## 1. 登場人物(アクター)

| アクター | 説明 |
|---|---|
| 顧客 (Customer) | 商品を注文し、代金を支払う人 |
| 加盟店 (Merchant / 自社) | ECサイトを運営し、顧客からの注文を受け付け、PSPを通じて代金を回収する事業者。本システム(`settlement`)そのもの |
| PSP (決済代行事業者 / Payment Service Provider) | 加盟店に代わってカード会社・銀行とのやり取りを行い、与信・売上確定・返金を実行する外部事業者(例: Stripe、決済代行会社等)。本演習では`pspsimulator`として模擬する |
| カード会社 / イシュア (Card Issuer) | 顧客にクレジットカードを発行している金融機関。PSPの先に存在し、本設計では直接は登場しない(PSPが決済処理を代理する) |

---

## 2. 境界づけられたコンテキスト

| コンテキスト | 関心事 | 関与しないこと |
|---|---|---|
| 注文 (Order) | 顧客が「何を」「いくつ」「いくらで」買うか | 代金がどう決済されるか |
| 決済 (Payment) | 注文に対する代金のやり取り(与信・売上確定・返金) | 何を買ったか。注文の内容には一切関与せず、注文はただの参照(ID)としてしか扱わない |

---

## 3. 注文コンテキストの用語集

| 用語 | 定義 |
|---|---|
| 注文 (Order) | 顧客が発注した商品・数量・金額の集合体。明細(何を・いくつ)を保持する |
| 顧客 (Customer) | 注文を行う主体 |

---

## 4. 決済コンテキストの用語集

| 用語 | 定義 |
|---|---|
| 注文 (Order) | 何をいくつ買ったかを一切持たない、単なる参照。「この決済がどの注文に対応するか」を紐づけるためだけに使う |
| 与信 (Authorize) | PSP(実質的にはカード会社)に対して、注文金額分の利用枠を一時的に確保してもらうこと。この時点ではまだ代金は引き落とされない |
| 与信枠 | 与信によって一時的に確保された利用可能額。有効期限があり、期限を過ぎると自動的に失効する |
| 売上確定 (Capture) | 与信で確保した枠の中から、実際に代金を引き落とすこと。与信した金額の範囲内でのみ行える |
| 返金 (Refund) | 売上確定によって引き落とし済みの代金の全部または一部を、顧客に払い戻すこと |
| Webhook通知 | PSPが与信・売上確定・返金の結果を、依頼を受け付けた時点では確定させず、後から非同期に加盟店(本システム)へ知らせる仕組み |
| 冪等性キー (Idempotency-Key) | PSPへの依頼が何らかの理由で重複して送られても、同じ操作が二重に実行されないようにするための識別子 |

---

## 5. コンテキストをまたぐ際の意味の違い

同じ単語でも、コンテキストが変われば意味・保持する情報が変わる。これは表記ゆれではなく、境界づけられたコンテキストが正しく機能している証拠である。

| 用語 | 注文コンテキストでの意味 | 決済コンテキストでの意味 |
|---|---|---|
| 注文 | 商品明細・数量・金額を持つ、完全な業務エンティティ | `OrderId`という単なる参照。明細や商品情報は一切持たない |

決済コンテキストは「何を買ったか」を知る必要が無いため、注文の中身を持ち込まない。もし決済側が注文明細まで参照し始めたら、それはコンテキストの境界が壊れているサインである。

## 6. 業務フロー(ライフサイクル)

### 注文のライフサイクル

1. 顧客が注文する → 注文は「受付中」
2. 決済(与信)が成功する → 注文は「確定」
3. 決済(与信)が失敗する → 注文は「取消」
4. 売上確定が完了する → 注文は「入金済み」(実際に代金を受け取った状態)
5. 返金が完了する → 注文は「返金済み」

### 決済のライフサイクル

1. 注文に紐づいて、PSPへ与信の依頼が発生する
2. PSPが与信を承認する、または拒否する
3. 与信が承認されたら、直ちに売上確定を行う(出荷等のタイミングを待たずに決済処理を行うという業務判断。詳細は[ADR-0001](./adr/0001-exclude-void-from-scope.md)を参照)
4. 売上確定が完了した後、顧客からの返品・キャンセル等の要求に応じて返金を行う(全額または一部)

---

## 7. 業務ルール(なぜそうなのか)

- **売上確定は与信した金額を超えられない**: 与信は「これだけ使う可能性がある」とカード会社に伝えて確保してもらった枠であり、それを超えて引き落とすことは取引上許されない
- **返金は売上確定した金額を超えられない**: 実際に受け取っていない金額を返すことはできない。受け取った以上の返金は不正な操作とみなされる
- **与信には有効期限がある**: カード会社が枠を無期限に確保し続けることはできないため、一定期間内に売上確定しないと与信は自動的に失効する
- **与信・売上確定・返金の依頼をした時点では、結果はすぐに分からない**: PSPの先にはカード会社や本人確認(3Dセキュア等)が絡む場合があり、依頼した時点では結果が確定せず、後から非同期に知らされる

---

## 8. 業務用語とシステム設計書の対応

| 業務用語 | 技術設計書での対応 |
|---|---|
| 注文 | `Order`集約 |
| 与信 | `Authorization`エンティティ、`AuthorizePaymentUseCase` |
| 売上確定 | `Capture`エンティティ、`CapturePaymentService` |
| 返金 | `Refund`エンティティ、`RefundPaymentUseCase` |
| 与信枠の失効 | `Authorization.expiresAt` |
| Webhook通知 | `PspWebhookController`、非同期のWebhook受信 |
| 冪等性キー | `Idempotency-Key`ヘッダー、`payment_psp_idempotency_keys` |
